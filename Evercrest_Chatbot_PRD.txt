1. Executive Summary
The Evercrest Tenant Work Order Chatbot is a production-grade, AI-powered conversational system that allows tenants of a property management organization to report maintenance issues and request work orders through natural language chat, with automated email dispatch to the relevant maintenance/admin staff, full administrative oversight, and embedded analytics.
This document specifies the complete system — application logic, AI integration, authentication, database, administrative tooling, and infrastructure — as a single, build-ready PRD. It is structured so that any engineer (or an AI coding agent such as Claude Code) can implement the system end-to-end from this document alone.
1.1 Goals
	•	Allow tenants to describe a maintenance issue conversationally and have the system structure it into a formal work order.
	•	Automatically notify the correct staff/admin via email when a work order is created.
	•	Give administrators full visibility into conversations, work orders, and system health through a dashboard with embedded analytics.
	•	Authenticate all users (tenants and admins) via secure, passwordless magic links, restricted to a managed whitelist.
	•	Run on a cost-efficient AI inference layer (Groq) instead of OpenAI, with no loss of functionality.
	•	Be deployable on a single VPS with a clean CI/CD pipeline.
1.2 Non-Goals
	•	This system does not handle payments, billing, or lease management.
	•	This system does not replace a full property management ERP — it is a focused work-order intake and tracking tool.
	•	Multi-language support is out of scope for v1 (English only), though the schema is designed to allow it later.

2.2 Core User Journeys
Journey A — Tenant reports an issue
	•	Tenant visits the landing page and clicks "Sign in."
	•	Tenant enters their email; if whitelisted, receives a magic link.
	•	Tenant clicks the link, is authenticated, and lands on the chat interface.
	•	Tenant describes their issue in natural language (e.g., "My kitchen sink has been leaking since yesterday").
	•	The AI (via Groq) asks clarifying questions if needed (unit number, urgency, preferred access time) and then confirms a structured work order summary.
	•	On confirmation, a Work Order record is created, and an email is automatically dispatched to the relevant admin/maintenance distribution list.
	•	Tenant sees a confirmation message with a work order reference number and can view its status later.
Journey B — Admin manages work orders
	•	Admin signs in via magic link (whitelisted admin email).
	•	Admin lands on the Admin Dashboard, seeing a live feed of new work orders and conversations.
	•	Admin can open any conversation transcript, view the structured work order, change its status (New → Acknowledged → In Progress → Resolved → Closed), and add internal notes.
	•	Admin can view analytics: volume over time, issue category breakdown, average resolution time, and SLA breaches.
	•	Admin can view system/audit logs (auth events, email dispatch logs, AI call logs) for troubleshooting and compliance.
Journey C — Email notification loop
	•	Work order created → system sends a "New Work Order" email to the admin distribution list via SMTP.
	•	Work order status changes → optional status-update email to the tenant.
	•	All outbound emails are logged in the email_logs table regardless of delivery success/failure.

3.1 Why Groq
Groq is used in place of OpenAI for all AI inference needs (chat responses, work-order data extraction, and dashboard analytics summarization) because it offers significantly lower per-token cost and very low latency for open-weight models such as Llama 3.x, while remaining OpenAI-compatible enough in API shape to require minimal code changes. All three AI-dependent features in this system are designed around a single shared Groq client module (Section 6).
3.2 Why a Free SMTP Tool
Magic-link emails and work-order notification emails are both transactional, low-volume (expected to be a few hundred emails/month at this stage), and do not require a paid transactional email service. A free-tier SMTP provider (or an existing organizational mailbox, e.g. Gmail/Google Workspace SMTP or Zoho Mail) is sufficient and keeps the cost of this system near-zero. The system is designed so the SMTP provider can be swapped later (e.g. to Postmark or SES) by changing only environment variables — no code changes.

4.2 Request Flow — Chat Message
	•	Tenant sends a message from /chat → POST /api/chat/message.
	•	Route handler validates the session (see Section 5), loads conversation history from messages table.
	•	Handler calls the shared Groq client (lib/ai/groq-client.ts) with the conversation history + system prompt.
	•	Groq returns a response. If the AI determines enough information has been gathered, it also returns a structured JSON extraction (issue category, urgency, unit number, description) — see Section 6.2.
	•	Response is persisted to messages. If a structured extraction was returned, a work_orders row is created/updated.
	•	If a new work order was just created, the email dispatch job fires asynchronously (Section 7).
	•	Response streamed/returned to the tenant UI.

5. Authentication System
5.1 Requirements Recap
	•	Passwordless magic-link authentication only. No password field anywhere in the system.
	•	Public sign-up is disabled. Only emails present in the allowed_emails whitelist table may request a magic link.
	•	Verified identity is forwarded to backend logic via the same mechanism used internally (we standardize on session-based auth rather than literal HTTP headers from a third-party IdP, since this system owns its own auth — see 5.5 for the header-compatibility note).

5.3 Token Design
	•	Magic link tokens are signed JWTs containing { email, purpose: "login", iat, exp }, signed with AUTH_SECRET.
	•	Expiry: 15 minutes.
	•	Single-use: on verification, the corresponding login_tokens row is marked used_at; a reused token is rejected even if not expired.
	•	On successful verification, a session is created: an HTTP-only, Secure, SameSite=Lax cookie containing a signed session JWT { userId, email, role, iat, exp }, expiry 7 days, refreshed on activity.
5.4 Email Whitelisting
	•	allowed_emails table stores every email permitted to request a magic link, plus their intended role (tenant or admin).
	•	POST /api/auth/request-link checks this table before sending any email. If the email is not present, the API returns a generic success-like response (e.g. "If this email is registered, a link has been sent") to avoid leaking which emails are valid — this is a security best practice, not optional.
	•	Admins manage this table through the Admin Dashboard (Section 9.4) — no redeploy required to add/remove an allowed email.
5.5 Header-Forwarding Compatibility Note
The original infrastructure brief described an external auth proxy forwarding identity via oai-authenticated-user-email / oai-authenticated-user-full-name headers. Because this PRD specifies the application as owning its own complete auth system (rather than sitting behind a third-party identity proxy), the application uses session cookies as its primary trust mechanism. For architectural compatibility, the system additionally exposes an internal middleware hook (middleware.ts) that, if these headers are present and the request originates from a configured trusted proxy IP, will auto-provision a session — this keeps the system pluggable behind such a proxy in the future without requiring it for v1.
5.6 Admin Elevation
	•	A user's role (tenant | admin) is set in the allowed_emails table and copied onto the users row at first login.
	•	All /admin/* pages and /api/admin/* routes check session.role === 'admin' server-side (in middleware and again in each route handler — defense in depth).

6. AI Integration (Groq)
6.1 Shared Groq Client
All AI calls go through a single module: lib/ai/groq-client.ts.
// lib/ai/groq-client.ts
import Groq from "groq-sdk";
 
const groq = new Groq({ apiKey: process.env.GROQ_API_KEY });
 
export const MODELS = {
  CHAT: "llama-3.3-70b-versatile",      // conversational responses
  EXTRACTION: "llama-3.1-8b-instant",    // fast structured extraction
  ANALYTICS: "llama-3.3-70b-versatile",  // dashboard summarization
} as const;
 
export async function groqChat(params: {
  model: string;
  messages: { role: "system" | "user" | "assistant"; content: string }[];
  jsonMode?: boolean;
  temperature?: number;
}) {
  const completion = await groq.chat.completions.create({
    model: params.model,
    messages: params.messages,
    temperature: params.temperature ?? 0.4,
    response_format: params.jsonMode ? { type: "json_object" } : undefined,
  });
  return completion.choices[0].message.content;
}

Environment variable required: GROQ_API_KEY. Never exposed client-side; only used in server-side route handlers.
6.2 Feature 1 — Conversational Chat Responses
	•	Model: llama-3.3-70b-versatile
	•	System prompt instructs the model to act as a property maintenance intake assistant: ask for unit number, issue category, description, urgency, and preferred access time if not already provided; otherwise confirm and summarize.
	•	Flow: every tenant message + full prior conversation history (capped at the last 20 messages for context-window/cost efficiency) is sent to Groq; the streamed response is shown in the chat UI.
6.3 Feature 2 — Work Order Data Extraction
	•	Model: llama-3.1-8b-instant (fast + cheap, used for structured extraction, not conversation)
	•	Trigger: after each tenant message, run an extraction pass in parallel with the chat response.
	•	Mode: jsonMode: true, with a system prompt instructing the model to output a strict JSON object matching the work_orders schema fields (category, urgency, unit_number, description, ready_to_submit: boolean).
	•	Logic: when ready_to_submit === true and the tenant confirms, the application creates a work_orders row from the extracted fields.
6.4 Feature 3 — Admin Dashboard Analytics Summaries
	•	Model: llama-3.3-70b-versatile
	•	Trigger: on-demand, when an admin opens the Analytics tab, or on a scheduled daily cron.
	•	Input: aggregated, pre-computed statistics (counts, averages — never raw PII) are passed to Groq, which returns a 2–4 sentence natural-language summary (e.g., "Work order volume is up 18% this week, driven primarily by plumbing issues in Building C. Average resolution time improved to 1.4 days.").
	•	Important: the AI is given pre-aggregated numbers, not raw conversation text, both for cost efficiency and to avoid PII exposure to the summarization step.
6.5 Cost & Rate-Limit Handling
	•	All Groq calls wrapped in a retry-with-backoff helper (3 attempts, exponential backoff) to handle Groq's rate limits gracefully.
	•	Token usage per call is logged to an ai_usage_logs table (model, prompt_tokens, completion_tokens, feature, created_at) for cost monitoring — this gives the admin a way to track AI spend over time even though Groq's cost is low.

7.2 SQLite (Local Dev) Notes
For local development, replace pgTable/enums with sqliteTable and represent enums as text columns with a CHECK constraint or application-level validation, and jsonb as text (JSON-stringified). Drizzle's migration tooling (drizzle-kit) supports generating from either dialect — keep db/schema.ts as the Postgres source of truth and maintain a parallel db/schema.sqlite.ts for local dev if full type-parity is desired, or simply point local dev at a lightweight Postgres Docker container to avoid schema drift entirely (recommended).
7.3 Migrations
	•	Use drizzle-kit generate to produce SQL migration files from schema changes.
	•	Use drizzle-kit migrate (run automatically by the CI/CD pipeline, Section 10) to apply migrations to staging/production on deploy.
	•	Never edit a migration file that has already been applied to production — always generate a new one.
7.4 Indexing Rationale
	•	work_orders.status and work_orders.created_at are indexed since the Admin Dashboard's primary queries filter/sort by these.
	•	messages.conversation_id is indexed since conversation transcripts are the most frequent read pattern.
	•	system_logs.event_type and created_at are indexed for audit log filtering.
7.5 Backup Strategy
	•	Automated daily pg_dump to a separate backup volume/object storage (e.g., a low-cost S3-compatible bucket), retained for 30 days on a rolling basis.
	•	Backup job runs as a cron on the VPS, outside the application process, and is logged to system_logs with event type system.backup_completed or system.backup_failed.
8. API Contracts
All API routes are implemented as Next.js Route Handlers under app/api/. All routes (except auth/request-link and auth/verify) require a valid session cookie. Admin routes additionally require role === "admin".
8.1 Authentication
`POST /api/auth/request-link`
Request a magic link.
Request body:
{ "email": "tenant@example.com" }

Response (always 200, regardless of whitelist status — see Section 5.4):
{ "message": "If this email is registered, a login link has been sent." }

Logic: Check allowed_emails. If found, generate token, insert login_tokens row, send email via SMTP. If not found, do nothing but return the same response.

`GET /api/auth/verify?token=...`
Verify a magic link token and create a session.
Response (success): 302 Redirect to /chat (tenant) or /admin (admin), with Set-Cookie: session=<jwt>; HttpOnly; Secure; SameSite=Lax. Response (invalid/expired/used token): 302 Redirect to /login?error=invalid_token.

`POST /api/auth/logout`
Clears the session cookie. Response: 200 { "message": "Logged out" }

8.2 Chat
`POST /api/chat/message`
Send a tenant message and receive the AI response.
Request body:
{
  "conversationId": 123,
  "message": "My kitchen sink has been leaking since yesterday"
}

If conversationId is omitted, a new conversation is created for the current session's user.
Response:
{
  "conversationId": 123,
  "reply": "Thanks for letting me know. Could you tell me your unit number and how urgent this feels — minor drip, or actively flooding?",
  "workOrderDraft": {
    "category": "plumbing",
    "urgency": null,
    "unitNumber": null,
    "description": "Kitchen sink leaking since yesterday",
    "readyToSubmit": false
  }
}

When readyToSubmit becomes true and the tenant confirms (see /api/chat/confirm below), a work order is created.

`POST /api/chat/confirm`
Tenant confirms the drafted work order summary, finalizing creation.
Request body:
{ "conversationId": 123 }

Response:
{
  "workOrder": {
    "id": 45,
    "referenceCode": "WO-20260625-0045",
    "status": "new"
  },
  "message": "Your work order WO-20260625-0045 has been submitted. Our team will reach out shortly."
}

Side effect: triggers email dispatch to the admin distribution list (Section 9).

`GET /api/chat/history?conversationId=123`
Returns full message history for a conversation (used to hydrate the chat UI on reload).
Response:

14. Platform Expansion — Multi-Property Tenant Portal
14.1 Scope Change Summary
The system specified in Sections 1–13 covered the chatbot, work-order workflow, and administrative tooling. This section extends that system into a full multi-property tenant portal, adding:
	•	Property and unit management (multiple buildings/complexes, each with its own units)
	•	Amenity booking (gym, pool, clubhouse, etc., with calendar-based reservations)
	•	Announcements/notices board
	•	Document center (lease documents, policies)
	•	Community/resident directory
All new content (properties, amenities, announcements, documents, directory visibility) is managed exclusively by admins through the Admin Dashboard — there is no separate property-manager role in v1, and no public self-service content creation.
Every module below is designed against the same patterns already established: Drizzle schema with indexes, Next.js route handlers with the standard error/auth conventions (Section 8.9, 5.6), and Groq used only where it adds real value (not forced into every feature).

14.5 API Contracts — New Modules
All routes follow the same auth and error conventions as Section 8. Tenant-facing routes are automatically scoped to session.propertyId; admin routes accept an explicit propertyId filter.
Properties & Units
`GET /api/properties` (public) — Lists active properties for the landing page property picker.
{ "properties": [ { "id": 1, "name": "Evercrest Riverside", "slug": "riverside", "city": "Toronto", "heroImageUrl": "..." } ] }

`GET /api/properties/:slug` (public) — Single property detail for its landing page.
`GET /api/admin/properties` / `POST /api/admin/properties` / `PATCH /api/admin/properties/:id` — Standard CMS CRUD for admins.
`GET /api/admin/properties/:id/units` / `POST .../units` — Manage units within a property.

Amenities & Booking
`GET /api/amenities` (tenant) — Lists amenities for the tenant's property.
{ "amenities": [ { "id": 5, "name": "Rooftop Pool", "requiresBooking": true, "openTime": "08:00", "closeTime": "22:00" } ] }

`GET /api/amenities/:id/availability?date=2026-07-01` (tenant) — Returns open slots for a given day, computed from bookingSlotMinutes minus existing amenityBookings.
{ "slots": [ { "start": "09:00", "end": "10:00", "available": true }, { "start": "10:00", "end": "11:00", "available": false } ] }

`POST /api/amenities/:id/bookings` (tenant) — Create a booking.
{ "startTime": "2026-07-01T09:00:00Z", "partySize": 2 }

Logic: server-side re-validates the slot is still free before committing (prevent race conditions on double-booking) — this check must happen inside a transaction, not just client-side.
`GET /api/amenities/bookings/mine` (tenant) — Tenant's own upcoming/past bookings.
`DELETE /api/amenities/bookings/:id` (tenant) — Cancel own booking (sets status: cancelled, does not hard-delete, for audit purposes).
`GET /api/admin/amenities` / CRUD — Admin manages amenity definitions (name, capacity, hours, images).
`GET /api/admin/amenities/bookings` — Admin view of all bookings, filterable by amenity/date/tenant.

Announcements
`GET /api/announcements` (tenant) — Active announcements for the tenant's property, sorted by priority then publishedAt descending, excluding expired ones.
`GET /api/admin/announcements` / `POST` / `PATCH /:id` / `DELETE /:id` — Standard CMS CRUD.

Documents
`GET /api/documents` (tenant) — Documents visible to the tenant: property-wide (tenantId IS NULL) plus any addressed specifically to them.
`GET /api/admin/documents` / `POST` (upload) / `DELETE /:id` — Admin manages documents. File upload uses the same VPS file-storage approach as Section 14.8 (static file serving, not a separate object-storage dependency for v1).

Resident Directory
`GET /api/directory` (tenant) — Lists only opted-in residents of the tenant's own property.
{ "entries": [ { "displayName": "Jordan M.", "unitNumber": "4B", "bio": "..." } ] }

Note: contactEmailVisible controls whether an email field is included per-entry; if false, no email is returned regardless of requester role.
`GET /api/directory/me` / `PATCH /api/directory/me` (tenant) — Tenant manages their own directory visibility and bio.
{ "showInDirectory": true, "contactEmailVisible": false, "bio": "Friendly neighbor, two cats." }

`GET /api/admin/directory` — Admin can view all entries (including opted-out, for moderation purposes only — never exposed to other tenants).

14.6 Groq Usage in New Modules
Per the original instruction that Groq should power "all" AI-driven aspects of this system, two additional touchpoints are in scope:
	•	Announcement drafting assistant (admin-only): On the admin announcement creation form, an optional "Draft with AI" button sends a short prompt (admin's bullet points) to Groq (llama-3.3-70b-versatile) and returns a polished announcement draft for the admin to edit before publishing. This is assistive only — admins always review before publishing, nothing is auto-published.
	•	Directory bio suggestions (tenant-optional): When a tenant fills out their directory bio, an optional "Suggest a friendly bio" button can lightly rephrase their own input via Groq. Entirely optional, never runs without the tenant clicking it.
No other new module requires AI — amenity booking and document access are deterministic, not generative, and forcing AI into them would add cost and latency with no user benefit.

14.10 File Storage for Uploads (Documents, Property/Amenity Images)
For v1, uploaded files (property hero images, amenity images, lease documents) are stored on the VPS's local filesystem under a dedicated /uploads directory, served statically via the Nginx reverse proxy with appropriate access control for tenant-specific documents (a signed, time-limited URL pattern — not a publicly guessable path). This avoids adding a third-party object storage dependency for v1, while keeping the storage layer abstracted behind a single lib/storage/ module so it can be swapped for S3-compatible storage later without touching calling code.

14.11 Updated Build Sequencing
The build order in Section 13 remains the foundation. Multi-property and portal modules are sequenced after the core chatbot/work-order/admin loop is functional, since that core loop is the highest-priority deliverable and the new modules depend on properties/units existing first:
1–13. (As specified in Section 13 — core chatbot, auth, work orders, base admin tooling)
	•	Properties & Units schema + admin CMS (Section 14.2, 14.9)
	•	Retrofit users, allowed_emails, work_orders, conversations with property/unit references (Section 14.3) — includes a data migration step for any records created before this point
	•	Real landing page + property pages with full copy (Section 14.7)
	•	Amenities + booking engine, including the availability/race-condition logic (Section 14.5)
	•	Announcements module + admin CMS
	•	Document center + file storage module (Section 14.10)
	•	Resident directory + tenant profile/privacy settings (Section 14.4, 14.8)
	•	Property-scoping retrofit of admin dashboards (filters, switcher) (Section 14.9)
	•	Full QA pass across property-scoping (verify no cross-property data leakage — this is the single highest-risk area of the whole expansion and deserves dedicated test cases)
	•	CI/CD, deployment, documentation handover (as in Section 13, repeated for the full expanded scope)
14.12 Key Risk to Flag
The single biggest technical risk introduced by this expansion is cross-property data leakage — e.g., a tenant at Property A seeing Property B's announcements, directory, or another tenant's documents because a query filter was missed. Every new tenant-facing query must filter by session.propertyId server-side (never trust a client-supplied property ID), and this should be a named item in QA sign-off, not an assumed side effect of "it looked right in testing."
